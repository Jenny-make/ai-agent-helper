# Codex Development Plan

## 项目目标

基于 Spring Boot + Spring AI 构建一个面向企业客服场景的智能客服系统，优先满足以下要求：

- 中国大陆网络环境可稳定接入
- 飞书作为第一接入渠道
- 模型层支持多 provider，当前优先 `MiniMax / DeepSeek / OpenAI-compatible`
- 知识检索使用 `Milvus`
- 架构清晰，便于后续继续由 Codex 接手开发

## 当前产品定位

当前阶段将项目定位为：

**飞书企业客服 Copilot / 客服中台 Agent 的第一版基座**

它不是单纯的聊天 Demo，也不是通用 Agent 框架，而是围绕“企业客服问答、知识检索、转人工兜底”设计的垂直应用骨架。

## 当前已完成能力

### 1. 模型接入骨架

- 已支持 `DeepSeek`
- 已支持 `MiniMax`
- 已支持 `OpenAI-compatible` 模型接入方式
- 已支持通过 `app.ai.provider` 做 provider 选择
- 已增加自动排除无关 Spring AI 自动配置的启动逻辑

### 2. 控制台问答验证链路

- 已提供本地控制台问答 Runner
- 可直接在控制台输入问题并获得模型回复
- 已增加超时、错误打印、自检输出，便于本地调试

### 3. RAG 骨架

- 已具备 `VectorStore` 检索接入点
- 已支持通过配置开关启用或关闭 RAG
- 已将检索结果注入回答流程

### 4. 飞书接入占位入口

- 已有飞书 Webhook Controller
- 已支持基本调试入口
- 但尚未完成真实飞书验签、事件解析、消息回发闭环

## 推荐架构分层

### 1. Channel 层

负责渠道接入与消息适配：

- 飞书事件接收
- 飞书验签
- 飞书消息回发
- 后续可扩展 Web / 工单系统 / 其他 IM

### 2. Orchestration 层

负责对话编排：

- 识别用户问题
- 判断是否启用知识检索
- 路由模型 provider
- 决定直接回复、兜底回复还是转人工

### 3. Knowledge 层

负责知识库处理：

- 文档导入
- 切片
- embedding
- Milvus 检索
- 引用片段输出

### 4. Safety / Policy 层

负责业务安全与策略：

- 敏感问题识别
- 规则命中
- 人工升级策略
- 输出约束

### 5. Ops / Admin 层

负责后台管理与运维：

- 配置管理
- 监控与健康检查
- 知识库维护
- 灰度开关

## 里程碑规划

### V0.1 飞书客服问答闭环版

目标：打通最小可用闭环。

范围：

- 飞书收消息
- 调用模型生成回复
- 回复飞书消息
- 保留控制台调试入口
- 失败时返回统一兜底话术

验收标准：

- 可以从飞书发消息触发回答
- 可以在本地控制台复现同一套回答链路
- 支持通过配置切换模型 provider

### V0.2 知识库客服版

目标：补齐 RAG 闭环。

范围：

- 文档导入接口
- 文档切片与 embedding
- Milvus 入库
- 检索增强回答
- 输出引用片段
- 未命中时触发兜底或转人工建议

验收标准：

- 能导入一批知识文档
- 对知识库内问题优先给出基于知识的回答
- 能看到检索命中的引用片段

### V0.3 企业可用版

目标：增加真实客服场景能力。

范围：

- 会话状态管理
- 敏感问题规则
- 转人工
- 审计日志
- 配置灰度

验收标准：

- 支持连续会话
- 对高风险问题不直接自由回答
- 支持人工接管与运营排查

## 下一阶段开发顺序

建议严格按以下顺序推进：

1. 完成飞书真实接入闭环
2. 完成知识文档导入与 Milvus 入库
3. 完成 RAG 引用与未命中兜底
4. 增加转人工与会话状态
5. 增加监控、审计与配置灰度

## 开发约束

- 保持 `controller -> orchestration/service -> knowledge/policy` 的清晰边界
- 不要把飞书协议细节散落到多个业务类中
- 短期不要引入复杂多 agent 机制
- 短期不要把项目做成通用 Agent 平台
- 每次阶段性改动同步更新文档与配置模板
