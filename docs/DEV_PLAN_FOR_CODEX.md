# Codex Development Plan

## 项目目标

基于 Spring Boot + Spring AI 构建一个面向企业客服场景的智能客服系统，优先满足以下要求：

- 中国大陆网络环境可稳定接入
- 飞书作为第一接入渠道
- 模型层支持多 provider，当前优先 `MiniMax / DeepSeek / OpenAI-compatible`
- 知识检索使用 `Milvus`
- 架构清晰，便于后续继续由 Codex 接手开发

## 当前产品定位

当前阶段将项目定位为：

**飞书企业客服 Copilot / 客服中台 Agent 的第一版基座**

它不是单纯的聊天 Demo，也不是通用 Agent 框架，而是围绕“企业客服问答、知识检索、转人工兜底”设计的垂直应用骨架。

## 当前已完成能力

### 1. 模型接入与启动治理

- 已支持 `DeepSeek`
- 已支持 `MiniMax`
- 已支持 `OpenAI-compatible` 模型接入方式
- 已支持通过 `app.ai.provider` 做 provider 选择
- 已增加自动排除无关 Spring AI 自动配置的启动逻辑
- 已支持在 `auto` 模式下按已配置 API Key 推断可用 provider

### 2. 控制台问答验证链路

- 已提供本地控制台问答 Runner
- 可直接在控制台输入问题并获得模型回复
- 已增加超时、错误打印、自检输出，便于本地调试
- 已支持同一 session 下的历史上下文复用与 `/history` 调试

### 3. 会话记忆与回答策略

- 已增加基于内存的会话记忆
- 已支持最近轮次保留 + 历史摘要压缩
- 已支持对模糊追问进行上下文消歧
- 已支持根据最新用户消息自动决定回答语言
- 已支持对“上一条回答改成中文 / 英文”等语言切换请求做重写
- 已增加 prompt 泄漏与元响应文本清洗

### 4. RAG 读取侧接入

- 已具备 `VectorStore` 检索接入点
- 已支持通过配置开关启用或关闭 RAG
- 已将检索结果注入回答流程
- 已提供向量库健康检查接口

### 5. 飞书基础接入闭环

- 已有飞书 Webhook Controller
- 已支持 `url_verification`
- 已支持 `im.message.receive_v1` 文本消息解析
- 已支持群聊 `@` 识别、消息清洗与重复投递去重
- 已支持通过飞书 Open API 回发文本消息
- 已支持租户访问令牌获取与缓存
- 已保留本地 debug 入口
- 但尚未完成加密事件解密与更严格的签名校验

## 推荐架构分层

### 1. Channel 层

负责渠道接入与消息适配：

- 飞书事件接收
- 飞书验签
- 飞书消息回发
- 后续可扩展 Web / 工单系统 / 其他 IM

### 2. Orchestration 层

负责对话编排：

- 识别用户问题
- 判断是否启用知识检索
- 路由模型 provider
- 决定直接回复、兜底回复还是转人工

### 3. Knowledge 层

负责知识库处理：

- 文档导入
- 切片
- embedding
- Milvus 检索
- 引用片段输出

### 4. Safety / Policy 层

负责业务安全与策略：

- 敏感问题识别
- 规则命中
- 人工升级策略
- 输出约束

### 5. Ops / Admin 层

负责后台管理与运维：

- 配置管理
- 监控与健康检查
- 知识库维护
- 灰度开关

## 里程碑规划

### V0.1 飞书客服问答闭环版

目标：完成飞书文本消息 MVP，并补齐生产前必须的安全收尾。

范围：

- 飞书文本消息收发
- 调用模型生成回复
- 回复飞书消息
- 保留控制台调试入口
- 补齐加密 / 签名校验
- 失败时返回统一兜底话术

验收标准：

- 可以从飞书发消息触发回答
- 可以在本地控制台复现同一套回答链路
- 支持通过配置切换模型 provider
- 飞书请求具备基础生产安全校验

### V0.2 知识库客服版

目标：补齐 RAG 闭环。

范围：

- 文档导入接口
- 文档切片与 embedding
- Milvus 入库
- 检索增强回答
- 输出引用片段
- 未命中时触发兜底或转人工建议

验收标准：

- 能导入一批知识文档
- 对知识库内问题优先给出基于知识的回答
- 能看到检索命中的引用片段

### V0.3 企业可用版

目标：增加真实客服场景能力。

范围：

- 持久化会话状态管理
- 敏感问题规则
- 转人工
- 审计日志
- 配置灰度

验收标准：

- 支持连续会话
- 对高风险问题不直接自由回答
- 支持人工接管与运营排查

## 下一阶段开发顺序

建议严格按以下顺序推进：

1. 完成知识文档导入与 Milvus 入库
2. 完成 RAG 引用输出与未命中兜底
3. 补齐飞书加密 / 签名校验与异常兜底
4. 增加转人工与持久化会话状态
5. 增加监控、审计与配置灰度

## 开发约束

- 保持 `controller -> orchestration/service -> knowledge/policy` 的清晰边界
- 不要把飞书协议细节散落到多个业务类中
- 短期不要引入复杂多 agent 机制
- 短期不要把项目做成通用 Agent 平台
- 每次阶段性改动同步更新文档与配置模板
