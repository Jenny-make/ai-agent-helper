# Codex Development Plan

更新时间：2026-04-19

## 项目目标

基于 Spring Boot + Spring AI 构建一个面向企业客服场景的智能客服系统，优先满足以下要求：

- 中国大陆网络环境可稳定接入
- 飞书作为第一接入渠道
- 模型层支持多 provider：`MiniMax / DeepSeek / OpenAI-compatible`
- 知识检索使用 Milvus，通过 Spring AI `VectorStore` 统一接入
- 架构边界清晰，便于后续继续由 Codex 接手开发

## 当前产品定位

当前阶段定位为：

**飞书企业客服问答 MVP / 客服中台 Agent 的第一版基座**

它不是通用 Agent 平台，而是围绕“企业客服问答、飞书消息闭环、企业知识库检索、后续转人工兜底”设计的垂直应用骨架。

## 当前已完成能力

### 1. 模型接入与启动治理

- 支持 `DeepSeek`、`MiniMax`、`OpenAI-compatible`。
- 支持通过 `app.ai.provider` 选择 provider。
- 支持 `auto` 模式，按已配置模型 bean 优先选择可用 provider。
- 增加 Spring AI 自动配置排除逻辑，避免未配置 provider 影响启动。

### 2. 控制台问答验证链路

- 提供本地控制台问答 Runner。
- 支持 `/new`、`/history`、`/session`、`/help`。
- 支持超时控制、错误打印和基础启动自检输出。
- 控制台和飞书共用 `KnowledgeAnswerService` 回答链路。

### 3. 会话记忆与回答策略

- 默认提供进程内会话记忆。
- 配置 JDBC / DataSource 后自动切换为数据库持久化会话记忆。
- 支持最近轮次保留、历史摘要压缩、简单事实回忆。
- 支持模糊追问消歧、独立问题避免污染历史上下文。
- 支持根据最新用户消息决定回复语言。
- 支持“把上一条改成中文/英文”等语言切换重写。
- 增加 prompt 泄漏、元响应、重复文本清洗和兜底。

### 4. RAG 问答链路

- 支持通过 `app.rag.enabled` 开关启用或关闭 RAG。
- 支持从 `VectorStore` 做相似度检索，并将检索证据注入回答。
- 支持 `topK`、相似度阈值、单片段最大字符数配置。
- 支持根据当前 session 的活跃文档构建检索过滤条件。
- 支持文档类问题在无证据时返回“不确定”的保守答案。
- 提供 `GET /api/admin/health/vector` 健康检查入口。

### 5. 飞书消息闭环

- 支持 `url_verification`。
- 支持 `im.message.receive_v1` 文本消息解析。
- 支持 p2p 自动回复、群聊必须显式 `@` 才回复。
- 支持 `@` 文本和 mentions 元数据清洗。
- 支持短窗口重复投递去重。
- 支持按聊天、线程、用户构造会话 ID。
- 支持租户访问令牌获取与缓存。
- 支持通过飞书 Open API 回复原消息。
- 支持 `/new` 命令清理当前会话记忆和活跃文档。
- 保留 `POST /api/feishu/debug/reply` 本地调试入口。

### 6. 飞书知识同步第一版

- 支持按 `docx` token 或链接拉取飞书文档纯文本。
- 支持 `wiki` 链接解析，当前限于底层对象为 `docx` 的 wiki 页面。
- 支持飞书文件夹作为同步根，递归展开嵌套文件夹、`docx` 和指向 `docx/folder` 的快捷方式。
- 支持本地切片，配置 `chunk-size`、`chunk-overlap`、`max-chunks-per-document`。
- 支持写入 `VectorStore / Milvus`，embedding 由 Spring AI 向量库配置承担。
- 支持本地同步状态文件保存上次 chunk ids，重复同步时先删旧 chunk 再写入。
- 支持 `POST /api/admin/knowledge/sync/feishu` 手动触发同步。
- 支持 `app.feishu.knowledge.auto-sync-on-startup` 启动时自动同步。

### 7. 数据库与测试

- 增加 Flyway migration：
  - `conversation_thread`
  - `conversation_message`
  - `active_document`
- 单元测试覆盖：
  - 飞书消息过滤、mention 清洗、重复投递、`/new`
  - 飞书知识同步和重复同步删除旧 chunk ids
  - 会话记忆摘要、数据库持久化
  - 文档问答、活跃文档过滤、语言切换、prompt 泄漏清洗

## 当前未完成的关键能力

### P0：上线前安全与 RAG 质量

- 飞书加密事件体解密。
- 更严格的请求签名 / 时间戳校验。
- 飞书回调异常时的统一兜底与可观测日志。
- RAG 引用片段更结构化地返回给调用方。
- RAG 未命中、低置信度、向量库异常时的客服兜底策略。

### P1：知识库生产化

- 知识同步状态从本地 JSON 文件迁移到数据库。
- 支持 PDF / DOC / PPT 等非 `docx` 文件解析。
- 支持完整 wiki 树同步，而不只是单个 wiki 页面。
- 支持按 Feishu 更新时间做增量同步。
- 支持多知识库、多租户、权限隔离。

### P2：企业客服能力

- 转人工。
- 工单衔接。
- 敏感问题识别。
- 审计日志。
- 限流、监控、告警、配置灰度。

## 推荐架构分层

### Channel 层

负责渠道接入与消息适配：

- 飞书事件接收
- 飞书验签和解密
- 飞书消息回发
- 后续扩展 Web / 工单系统 / 其他 IM

### Orchestration 层

负责对话编排：

- 识别任务模式
- 判断是否启用知识检索
- 路由模型 provider
- 管理会话记忆与活跃文档
- 决定直接回复、兜底回复或转人工

### Knowledge 层

负责知识库处理：

- 文档发现
- 文本抽取
- 切片
- embedding / Milvus 入库
- 检索和引用片段输出

### Safety / Policy 层

负责业务安全与策略：

- 敏感问题识别
- 规则命中
- 人工升级策略
- 输出约束

### Ops / Admin 层

负责后台管理与运维：

- 配置管理
- 监控与健康检查
- 知识库维护
- 同步任务管理
- 灰度开关

## 里程碑规划

### V0.1 飞书客服问答闭环版

目标：完成飞书文本消息 MVP，并补齐生产前必须的安全收尾。

已完成：

- 飞书文本消息收发。
- 调用模型生成回复。
- 回复飞书原消息。
- 控制台调试入口。
- provider 配置切换。
- 会话记忆与 `/new`。

剩余：

- 加密事件解密。
- 签名校验。
- 异常兜底与基础可观测性。

### V0.2 知识库客服版

目标：补齐可验证的 RAG 闭环。

已完成：

- 飞书 `docx/wiki/folder` 第一版同步。
- 本地切片。
- `VectorStore/Milvus` 写入。
- 检索增强回答。
- 活跃文档过滤。

剩余：

- 引用片段结构化输出。
- 未命中/低置信度策略。
- 同步状态持久化。
- 更多文件类型和完整 wiki 树同步。

### V0.3 企业可用版

目标：增加真实客服场景能力。

范围：

- 转人工。
- 工单衔接。
- 敏感问题规则。
- 审计日志。
- 限流与监控。
- 多租户与权限隔离。

## 下一阶段开发顺序

1. 补齐飞书加密事件解密、签名校验和异常兜底。
2. 增强 RAG 引用输出、未命中兜底和低置信度处理。
3. 将飞书知识同步状态迁移到数据库。
4. 增加更多文件类型解析和完整 wiki 树同步。
5. 增加转人工、工单、审计和监控。

## 开发约束

- 保持 `controller -> service/orchestration -> knowledge/policy` 的清晰边界。
- 不要把飞书协议细节散落到多个业务类中。
- 短期不要引入复杂多 agent 机制。
- 短期不要把项目做成通用 Agent 平台。
- 文档必须跟随阶段性改动更新，尤其是已完成/未完成边界。
